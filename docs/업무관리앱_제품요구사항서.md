# 팀 업무 관리 앱 — 제품 요구사항서(PRD)

- 문서 상태: 인터뷰 기반 초안
- 작성일: 2026-09-08
- 대상 사용자: 소규모 개발·제품팀
- 초기 사용 규모: 1~5명
- 문서 목적: 팀의 업무 진행 상황을 한눈에 파악할 수 있는 첫 번째 제품의 범위와 요구사항 정리

---

## 1. 제품 개요

### 1.1 제품 한 줄 설명

> 메신저와 이메일에 흩어진 개발 업무를 하나의 팀 보드에 모으고, 각 업무의 현재 진행 상태를 즉시 파악하게 해주는 반응형 업무 관리 앱.

### 1.2 해결하려는 문제

현재 팀은 메신저와 이메일을 중심으로 업무를 관리하고 있다. 이 방식에서는 다음 문제가 발생한다.

- 업무가 대화 흐름 속에 묻혀 진행 상황을 한눈에 보기 어렵다.
- 누가 어떤 업무를 담당하고 있는지 즉시 파악하기 어렵다.
- 업무 상태를 확인하기 위해 별도로 질문하거나 회의해야 한다.
- 마감일이 있는 업무를 놓칠 가능성이 있다.
- 주간 단위로 어떤 업무를 할지 계획하고 추적하기 어렵다.

### 1.3 가장 중요한 제품 목표

**팀원이 메신저나 별도 회의에서 묻지 않아도 팀의 업무 진행 상황을 즉시 파악할 수 있게 한다.**

### 1.4 성공 기준

1. 팀 보드만 확인해도 각 업무의 상태, 담당자, 우선순위, 마감일을 파악할 수 있다.
2. 팀원이 자신의 오늘 업무와 지연 업무를 바로 확인할 수 있다.
3. 주간 계획에 포함된 업무를 팀원이 자율적으로 선택할 수 있다.
4. 진행 중 업무가 지나치게 많아지는 상황을 팀 전체 기준으로 인지할 수 있다.
5. 업무 상태 변경을 위해 별도 문서나 메신저를 다시 업데이트할 필요가 없다.

## 2. 사용자와 사용 환경

### 2.1 초기 사용자

- 소규모 개발·제품팀
- 초기 사용자 수: 1~5명
- 팀원 모두가 하나의 팀 보드를 공유
- 팀원은 업무를 직접 선택하고 진행
- 관리자는 팀과 보드 설정을 담당

### 2.2 사용자 역할

#### 관리자

- 팀 설정 관리
- 팀원 초대
- 보드 및 상태 설정 관리
- 팀 전체의 업무 현황 확인
- 필요 시 진행 중 업무 한도 조정

#### 일반 멤버

- 업무 조회
- 백로그에서 이번 주 업무 선택
- 업무 상태 변경
- 체크리스트 업데이트
- 상태 메모 작성
- 댓글 및 파일·링크 추가
- 자신이 담당한 업무 완료 처리

### 2.3 접근 환경

- 반응형 웹 우선
- 데스크톱과 모바일 브라우저 모두 지원
- 모바일 웹 푸시 알림 고려
- 네이티브 iOS·Android 앱은 초기 범위에서 제외

### 2.4 로그인과 팀 참여

- Google 로그인 우선
- 초대 링크를 통한 팀 참여
- 관리자와 일반 멤버의 2단계 권한
- 팀 보드의 업무는 모든 팀원에게 공개

## 3. 핵심 업무 모델

### 3.1 업무(Task)

업무는 기능 개발, 개선, 기술 부채 등 개발팀이 처리해야 하는 단위 작업이다.

#### 핵심 필드

| 필드 | 필수 여부 | 설명 |
|---|---:|---|
| 제목 | 필수 | 업무를 짧게 설명하는 이름 |
| 업무 유형 | 권장 | 기능·스토리, 개선·기술 부채 등 |
| 담당자 | 선택 | 백로그에 먼저 등록한 뒤 나중에 지정 가능 |
| 상태 | 필수 | 백로그, 예정, 진행, QA, 완료 |
| 마감일 | 선택 | 마감일이 없는 업무도 허용 |
| 우선순위 | 권장 | 긴급, 높음, 보통, 낮음 |
| 설명 | 선택 | 요구사항 및 상세 맥락 |
| 상태 메모 | 선택 | 현재 상황을 한 줄로 요약 |
| 체크리스트 | 선택 | 업무를 구성하는 세부 작업 목록 |
| 외부 링크 | 선택 | 문서·디자인 등 관련 URL 여러 개 |
| 첨부파일 | 선택 | 스크린샷, 로그 등 업무 자료 |
| 댓글 | 선택 | 업무 관련 협업 논의 |
| 변경 이력 | 자동 | 모든 주요 변경 기록 |

### 3.2 업무 제목 규칙

업무 유형을 제목 앞에 붙이는 방식을 권장한다.

- `[기능] 결제 화면 추가`
- `[개선] 검색 API 응답 속도 개선`
- `[기술 부채] 인증 모듈 리팩터링`

첫 버전에서는 입력을 강제하기보다 유형 선택 시 예시·플레이스홀더로 안내한다.

### 3.3 업무 유형

인터뷰에서 우선 확인된 유형은 다음과 같다.

- 기능·스토리
- 개선·기술 부채

버그·장애 업무는 같은 보드에서 관리할 수 있도록 확장 가능한 구조로 설계한다. 버그를 첫 버전부터 별도 유형으로 노출할지는 추가 확인이 필요하다.

### 3.4 담당자

- 리더가 담당자 없이 업무를 백로그에 등록할 수 있어야 한다.
- 팀원은 백로그에서 이번 주에 할 업무를 자율적으로 선택할 수 있다.
- 담당자 없는 업무와 담당 업무를 명확히 구분한다.
- 담당자 변경은 변경 이력에 기록한다.

### 3.5 마감일

- 마감일 없는 업무를 허용한다.
- 마감일이 있는 업무는 내 업무 화면에서 가까운 순으로 우선 표시한다.
- 마감일 하루 전에 알림을 보낸다.
- 마감일이 지나면 지연 상태로 시각적으로 강조한다.
- 마감일이 없는 업무에 임의의 기본 날짜를 자동 설정하지 않는다.

### 3.6 우선순위

초기 우선순위는 다음 네 단계로 제공한다.

1. 긴급
2. 높음
3. 보통
4. 낮음

우선순위는 카드에서 간결하게 표시하고, 필요하면 필터 조건으로 사용할 수 있도록 한다.

## 4. 상태와 칸반 흐름

### 4.1 기본 상태

```text
백로그 → 예정 → 진행 → QA → 완료
```

- **백로그**: 아직 주간 계획에 넣지 않았거나 담당자가 정해지지 않은 업무
- **예정**: 처리하기로 계획했지만 아직 착수하지 않은 업무
- **진행**: 현재 개발 중인 업무
- **QA**: 개발이 끝나 테스트·검증 중인 업무
- **완료**: 담당자가 테스트 완료를 확인하고 종료한 업무

### 4.2 상태 변경

- 칸반 카드 드래그 앤 드롭으로 상태 변경
- 카드 상세 화면에서도 상태 변경 가능
- 상태 변경 시 변경 이력 자동 생성
- 완료 처리는 담당자만 수행 가능
- 완료된 업무는 기본 보드에서 자동 보관
- 완료 업무 보기에서 과거 업무를 검색·확인 가능

### 4.3 QA 운영

QA는 별도 상태 열로 표시한다. QA 결과를 기록할 수 있는 간단한 상태 메모 또는 댓글을 제공한다.

초기 완료 조건:

1. 개발 작업이 완료됨
2. 업무가 QA 상태에 있음
3. 테스트·검증이 끝남
4. 담당자가 업무를 완료 처리함

QA 담당자를 별도로 지정할지는 후속 인터뷰에서 결정한다.

### 4.4 막힘 표시

업무가 진행되지 못하는 경우를 위해 다음을 지원한다.

- 업무에 막힘 여부 표시
- 막힘 사유 입력
- 막힘 사유를 상태 메모 또는 상세 영역에서 확인

차단 업무 간 연결 기능은 후속 범위로 둘 수 있다.

## 5. 주간 계획과 스프린트

### 5.1 운영 방식

- 1주 단위로 계획
- 팀원이 백로그에서 이번 주 업무를 자율적으로 선택
- 이번 주 업무를 별도로 묶어 확인
- 1주가 끝난 뒤 미완료 업무는 다음 주로 자동 이동

### 5.2 첫 버전의 스프린트 범위

첫 버전에서는 복잡한 스프린트 관리보다 다음 기능에 집중한다.

- 업무를 `이번 주`로 지정하거나 해제
- `이번 주 업무` 필터·보기
- 미완료 업무의 다음 주 자동 이동
- 내 업무 화면에서 이번 주 업무 강조

스프린트 시작·종료 화면, 정교한 스프린트 회고, 속도·번다운 통계는 후순위로 둔다.

### 5.3 업무량 제한(WIP)

팀 전체의 `진행` 상태 업무 수를 제한하는 요구가 있다. 다만 구체적인 한도 숫자와 동작 방식은 아직 결정되지 않았다.

결정 전 권장안:

- 관리자가 팀 전체 WIP 한도를 설정
- 한도 초과 시 진행 열 상단에 경고 표시
- 업무 이동을 강제로 막기보다는 경고부터 제공
- 현재 진행 업무 수와 설정 한도를 함께 표시

예시:

```text
진행 중 3 / 권장 한도 3
WIP 한도를 초과하면 팀 전체에 경고를 표시합니다.
```

초기에는 이동을 차단하지 않고 시각적 경고만 제공하는 방식을 권장한다. 작은 팀에서 업무 흐름을 과도하게 막지 않으면서도 병목을 관찰할 수 있기 때문이다.

## 6. 주요 화면

### 6.1 내 업무 화면 — 기본 시작 화면

로그인 후 가장 먼저 표시되는 화면이다.

#### 우선 표시 영역

1. 오늘 처리할 업무
2. 지연된 업무
3. 마감일이 가까운 업무
4. 이번 주 업무
5. 상태별 내 업무

#### 기본 정렬

- 마감일이 가까운 순
- 마감일이 없는 업무는 별도 그룹 또는 하단 표시
- 지연 업무는 상단 고정 및 시각적 강조

#### 카드 표시 정보

- 제목
- 업무 유형
- 상태
- 우선순위
- 마감일
- 체크리스트 완료율
- 막힘 표시

### 6.2 팀 보드

하나의 팀 보드에서 전체 업무를 관리한다.

#### 칸반 보기

- 상태별 열 표시
- 카드 드래그로 상태 변경
- 핵심 정보만 간결하게 표시
- 카드 내 체크리스트 완료율 표시
- 완료 업무는 기본적으로 자동 보관

#### 리스트 보기

- 업무를 행 단위로 표시
- 제목, 담당자, 상태, 우선순위, 마감일, 체크리스트 진행률 표시
- 마감일 가까운 순 기본 정렬
- 검색·필터 제공

#### 보기 전환

- 칸반 ↔ 리스트 전환
- 선택한 보기와 필터를 사용자별로 기억하는 것은 후속 개선으로 고려

### 6.3 업무 상세 화면

업무 카드를 클릭하면 상세 화면 또는 패널을 연다.

#### 우선순위가 높은 영역

- 체크리스트
- 상태
- 담당자
- 마감일
- 우선순위
- 한 줄 상태 메모
- 댓글 및 진행 기록
- 외부 링크
- 첨부파일
- 변경 이력

#### 체크리스트

- 항목 추가·수정·삭제
- 완료 체크
- 전체 완료율 표시
- 카드와 상세 화면에 완료율 표시

담당자·개별 마감일을 체크리스트 항목별로 설정하는 기능은 후순위로 둘 수 있다.

### 6.4 완료 업무 보기

자동 보관된 완료 업무를 확인하는 별도 화면이다.

- 완료 업무 검색
- 완료일 표시
- 담당자·유형·기간 필터
- 업무 상세 열람
- 필요 시 복구 또는 재활성화

## 8. 협업과 기록

### 8.1 상태 메모

업무의 현재 상황을 한 줄로 남긴다.

예시:

- `API 개발 중, 오늘 오후까지 1차 완료 예정`
- `디자인 링크 확인 필요`
- `QA 환경 데이터 문제로 대기 중`

### 8.2 댓글

업무 카드 안에서 관련 논의를 남긴다.

- 업무 참여자에게 댓글 알림
- 댓글 작성자, 작성 시간 표시
- 댓글 수정·삭제 정책은 후속 결정

### 8.3 변경 이력

모든 변경을 상세히 기록한다.

기록 대상 예시:

- 제목 변경
- 설명 변경
- 담당자 변경
- 상태 변경
- 마감일 변경
- 우선순위 변경
- 체크리스트 추가·완료·삭제
- 링크·파일 추가·삭제
- 댓글 작성·수정·삭제
- 이번 주 업무 지정·해제

이력에는 다음을 포함한다.

- 변경한 사용자
- 변경 시각
- 변경 대상
- 변경 전 값
- 변경 후 값

## 9. 알림

### 9.1 초기 알림 범위

- 마감일 하루 전 알림
- 마감일이 지난 업무 알림 또는 화면 강조
- 업무 참여자에게 댓글·상태 메모 업데이트 알림

### 9.2 알림 채널

- 브라우저 푸시
- 모바일 웹 푸시
- 앱 내부 알림

네이티브 모바일 앱 푸시는 초기 범위에서 제외한다.

### 9.3 알림 원칙

- 알림 종류별 켜기·끄기 설정을 고려
- 동일한 업무의 연속 변경으로 알림이 과도하게 발생하지 않도록 그룹화 고려
- 사용자가 알림을 끄더라도 내 업무 화면의 지연·임박 표시에는 영향을 주지 않음

## 10. 첨부자료

### 10.1 외부 링크

업무마다 여러 개의 URL을 첨부할 수 있다.

주요 대상:

- Notion
- Figma
- Google Docs
- 기타 문서·디자인 도구

링크별 저장 정보:

- 링크 이름
- URL
- 추가한 사용자
- 추가 시각

### 10.2 파일 업로드

스크린샷, 로그, 기획 자료 등의 파일을 업무에 직접 업로드할 수 있어야 한다.

초기 고려 사항:

- 파일명과 업로더 표시
- 파일 업로드·다운로드
- 파일 삭제 권한
- 이미지 미리보기
- 허용 파일 크기와 확장자 제한
- 팀원 전체 공개 정책에 따른 접근 제어

파일 저장·보안 정책은 구현 전에 별도 확정한다.

## 11. 권한과 데이터 공개

### 11.1 권한 모델

| 기능 | 관리자 | 일반 멤버 |
|---|---:|---:|
| 팀 보드 조회 | 가능 | 가능 |
| 업무 생성 | 가능 | 가능 여부 후속 결정 |
| 업무 수정 | 가능 | 가능 |
| 상태 변경 | 가능 | 가능 |

### 11.2 공개 범위

- 기본적으로 팀 보드의 모든 업무는 팀원 전체 공개
- 초기에는 프로젝트별 비공개 권한을 제공하지 않음
- 관리자·일반 멤버 2단계 권한으로 시작

## 13. 대표 사용자 시나리오

### 시나리오 1: 리더가 백로그 업무 등록

1. 리더가 Google 로그인
2. 팀 보드에서 `업무 추가` 클릭
3. `[기능] 결제 화면 추가` 제목 입력
4. 설명과 문서 링크 추가
5. 담당자 없이 백로그에 저장
6. 팀원들이 백로그에서 업무를 확인

### 시나리오 2: 팀원이 이번 주 업무 선택

1. 팀원이 `내 업무` 또는 `이번 주 업무` 화면 확인
2. 백로그에서 처리할 업무 선택
3. 자신을 담당자로 지정
4. 업무를 `예정` 상태로 이동
5. 필요하면 마감일과 우선순위 설정

### 시나리오 3: 개발 진행

1. 업무를 `진행` 상태로 이동
2. 체크리스트를 추가하고 작업 단계를 기록
3. 한 줄 상태 메모 작성
4. 관련 Figma·Notion 링크와 파일 첨부
5. 카드에서 체크리스트 완료율 확인

### 시나리오 4: QA 처리

1. 개발 완료 후 업무를 `QA` 상태로 이동
2. 테스트 관련 체크리스트를 완료
3. QA 결과를 상태 메모 또는 댓글로 기록
4. 담당자가 업무를 `완료` 상태로 이동
5. 업무가 자동 보관되고 완료 업무 보기에서 확인 가능

### 시나리오 5: 지연 업무 확인

1. 담당자가 `내 업무` 화면에 접속
2. 지연 업무가 최상단에 표시됨
3. 업무 상세에서 막힘 사유 확인
4. 상태 메모 또는 댓글로 상황 공유
5. 팀원은 별도 질문 없이 최신 상황 확인

## 16. 권장 다음 단계

1. 팀의 실제 업무 10~20개를 수집한다.
2. 업무를 상태별로 분류해 기본 상태가 충분한지 검증한다.
3. 현재 진행 중인 업무 수를 조사해 초기 WIP 한도를 정한다.
4. 일주일간 종이·스프레드시트로 `이번 주 업무` 운영을 시뮬레이션한다.
5. MVP 프로토타입에서 다음 세 흐름을 먼저 검증한다.
   - 업무 등록 → 담당자 선택 → 진행 상태 변경
   - 내 업무에서 오늘·지연 업무 확인
   - 업무 상세에서 체크리스트와 상태 메모 업데이트
6. 소규모 팀원 2~3명에게 프로토타입을 사용하게 하고, 다음 질문으로 평가한다.
   - 지금 누가 무엇을 하는지 바로 알 수 있는가?
   - 업무를 등록하고 맡는 과정이 빠른가?
   - 상태를 업데이트할 이유와 위치가 분명한가?
   - 알림이 유용한가, 방해가 되는가?

## 17. 제품 원칙

- **현재 상태가 가장 중요하다.** 과거 기록보다 지금 무엇이 진행 중인지 빠르게 보여준다.
- **업데이트 비용을 낮춘다.** 상태 변경과 메모 작성을 짧고 쉽게 만든다.
- **작은 팀에 맞게 단순하게 시작한다.** 복잡한 권한·리포트·자동화는 나중에 추가한다.
- **업무는 투명하게 공개한다.** 팀원 모두가 전체 흐름을 볼 수 있게 한다.
- **계획보다 실제 흐름을 우선한다.** 주간 계획은 제공하되 미완료 업무가 자연스럽게 다음 주로 이어지게 한다.
- **경고하되 과도하게 막지 않는다.** WIP 한도는 팀의 흐름을 돕기 위한 신호로 시작한다.
